1.1 ภาพรวมระบบและการจำลองการทำงานจริง (8 Use Cases)

ระบบร้านอาหาร "ข้าวต้มอารมณ์ดี" (Khao Tom Arom Dee) เป็นโครงงานพัฒนาระบบตามระเบียบวิธีวิเคราะห์และออกแบบเชิงวัตถุ (Object-Oriented Analysis and Design: OOAD) ตั้งแต่ระยะ P1 ถึง P8 และถูกแปลงเป็นซอร์สโค้ดภาษา Java ในระยะ P9 โดยจำลองการทำงานผ่านคอนโซล (Text Mode Console) เพื่อให้ผู้เรียนสามารถทำความเข้าใจโครงสร้างเชิงวัตถุได้อย่างบริสุทธิ์โดยไม่มีความซับซ้อนของเฟรมเวิร์กเว็บหรือฐานข้อมูลมาบดบัง

ระบบประกอบด้วยงานหลัก 8 ด้าน (Use Cases) ที่ครอบคลุมการดำเนินงานทั้งหมดของร้านอาหาร ได้แก่:

รหัส UC ชื่องาน (Use Case) ผู้ใช้งานหลัก (Actors) ความรับผิดชอบหลักของระบบ

UC02 จัดการคู่มือ SOP ผู้จัดการ / เชฟใหญ่ สร้างคู่มือมาตรฐานการปรุงอาหาร, กำหนดขั้นตอนย่อยและเวลา, เผยแพร่ และปิดใช้งาน
UC03 ปรุงอาหารและเสิร์ฟ คนครัว / พนักงานเสิร์ฟ เลือกสถานีครัว, รับออเดอร์เข้าคิว, เริ่มปรุง, จับเวลาเทียบ SOP, เสิร์ฟถึงโต๊ะ

1.2 มโนทัศน์ OOP ที่นำมาใช้ในระบบร้านข้าวต้มอารมณ์ดี

1. Encapsulation (การห่อหุ้มและการซ่อนข้อมูล)

ฟิลด์ข้อมูลทั้งหมดใน 16 คลาสโมเดลถูกประกาศเป็น private อย่างเคร่งครัด เพื่อป้องกันไม่ให้อ็อบเจกต์ภายนอกหรือคลาส Main แก้ไขค่าได้โดยพลการ เช่น ยอดสต็อก stockQty ใน Ingredient ไม่สามารถถูกเขียนทับด้วยเครื่องหมายเท่ากับ (=) ได้ แต่จะต้องผ่านเมธอดทางธุรกิจ เช่น deduct(), receive() หรือ adjustStock() เท่านั้น ซึ่งแต่ละเมธอดจะมีเงื่อนไขตรวจสอบ (Validation) และจะสร้างประวัติ StockMovement เสมอ

2. Invariants & State Validation (การรักษาสภาวะความถูกต้องของระบบ)

ทุกอ็อบเจกต์มีหน้าที่รักษากฎความถูกต้องของตนเอง (Invariants) หากมีคำสั่งใดที่ขัดแย้งกับกฎ อ็อบเจกต์จะโยน Exception ออกมาทันที:

  • IllegalArgumentException: ใช้เมื่อพารามิเตอร์ที่ส่งเข้ามาไม่ถูกต้อง เช่น เบอร์โทรศัพท์ไม่ใช่ 10 หลัก (!phone.matches("0[0-9]{9}")), ปริมาณติดลบ, หรือราคาอาหารเท่ากับ 0
  • IllegalStateException: ใช้เมื่อพยายามทำงานที่ขัดกับสถานะปัจจุบันของอ็อบเจกต์ เช่น พยายามเปิดขายเมนูที่ยังไม่มีสูตรสมบูรณ์ (currentRecipe() == null), พยายามยกเลิกอาหารที่เริ่มปรุงไปแล้วโดยไม่ผ่านผู้จัดการ, หรือพยายามรับของซ้ำในใบสั่งซื้อที่รับไปแล้ว

3. Class Scope (static) vs Instance Scope

ในคลาส Member มีการประยุกต์ใช้ static ได้อย่างชัดเจน:

  • Instance Variables: memberId, name, phone, points และ transactions เป็นของสมาชิกแต่ละคน (แต่ละอ็อบเจกต์มีค่าของตัวเอง)
  • Static Variables (Class Level): bahtPerPoint (50 บาท/แต้ม), pointValue (1 บาท/แต้ม), และ minRedeem (10 แต้ม) เป็นกฎกลางของร้านอาหาร เมื่อผู้จัดการแก้ไขผ่าน Member.setRule() จะมีผลบังคับใช้กับสมาชิกทุกคนในร้านทันทีโดยไม่ต้องไปแก้ในสมาชิกทีละคน

1.3 Association (has-a) vs Composition (owns-a)

หนึ่งในหัวใจสำคัญที่สุดของการออกแบบเชิงวัตถุคือการทำความเข้าใจความสัมพันธ์แบบ has-a ซึ่งใน UML และ OOAD แบ่งออกเป็น 2 ประเภทหลัก:

มิติการเปรียบเทียบ Association (ความสัมพันธ์แบบรู้จักกัน / has-a) Composition (ความเป็นเจ้าของส่วนประกอบ / owns-a)
สัญลักษณ์ UML เส้นตรงธรรมดา หรือเส้นมีหัวลูกศรทิศทางเดียว (──>) เส้นตรงที่มี สัญลักษณ์ข้าวหลามตัดทึบ (◆) อยู่ฝั่งเจ้าของ
ความเป็นเจ้าของ ต่างฝ่ายต่างมีชีวิตเป็นของตัวเอง (Loose relationship) ฝั่ง Composite เป็นเจ้าของส่วนประกอบย่อย (Part-of) โดยสมบูรณ์
วงจรชีวิต (Lifecycle) เป็นอิสระต่อกัน การทำลายอ็อบเจกต์หนึ่งไม่ส่งผลต่ออีกอ็อบเจกต์ ผูกติดกัน (Bound lifecycle) เมื่ออ็อบเจกต์แม่ถูกทำลาย ส่วนย่อยจะถูกทำลายตามไปด้วย

1.4 หลักฐานเชิงประจักษ์ของ Composition ทั้ง 5 คู่ในโค้ด Java

เนื่องจากภาษา Java มีระบบ Garbage Collection ที่จัดการคืนหน่วยความจำอัตโนมัติ การแสดงความเป็น Composition ในระดับโค้ดจึงแสดงออกผ่าน 3 ปัจจัยหลัก:

  1. การถือครองข้อมูล: อ็อบเจกต์แม่เก็บ List ของอ็อบเจกต์ลูกไว้ภายใน
  2. การให้กำเนิด: อ็อบเจกต์แม่มีเมธอดสร้างอ็อบเจกต์ลูกขึ้นมาเอง เช่น order.addItem(...) สร้าง OrderItem, sop.addStep(...) สร้าง SOPStep
  3. การทำลายวงจรชีวิต (Lifecycle Cascade): อ็อบเจกต์แม่มีเมธอด destroy() ที่จะวนลูปเรียก destroy() ของอ็อบเจกต์ลูกทุกตัวก่อนที่จะเคลียร์ List ทิ้ง
อ็อบเจกต์แม่ (Composite) อ็อบเจกต์ลูก (Part-of) เมธอดสร้างลูก (Creation) หลักฐานการทำลาย (destroy cascade) ในโค้ดจริง
Order OrderItem order.addItem(...) for (OrderItem item : items) item.destroy(); items.clear();
Menu Recipe menu.addRecipe(...) for (Recipe r : recipes) r.destroy(); recipes.clear();
SOP SOPStep sop.addStep(...) for (SOPStep s : steps) s.destroy(); steps.clear();
Ingredient StockMovement ingredient.changeStock(...) for (StockMovement m : movements) m.destroy(); movements.clear();
Member PointTransaction member.addTransaction(...) for (PointTransaction t : transactions) t.destroy(); transactions.clear();

บทบาทหน้าที่ (Responsibility): ทำหน้าที่เป็นตัวแทนของวัตถุดิบแต่ละชนิดในคลังสินค้า ควบคุมยอดคงเหลือ (stockQty), ยอดจุดสั่งซื้อขั้นต่ำ (minQty), การตัดสต็อกเมื่อขาย, การคืนสต็อกเมื่อยกเลิก, การรับเข้าจากใบสั่งซื้อ, และการปรับยอด พร้อมทั้งเป็นเจ้าของประวัติ StockMovement

ตารางเมธอดสำคัญ (Key Methods & Operations)

hasEnough(double qty) : boolean Check / Invariant ตรวจสอบว่าสต็อกมีเพียงพอต่อจำนวนที่ต้องการตัดหรือไม่ (มี delta 0.000001 ป้องกันปัญหา floating point)
changeStock(double change, String type, ...) Core Helper (private) ปรับปรุงยอด stockQty และสร้างอ็อบเจกต์ StockMovement เพิ่มลงใน List ทันที

restore(double qty, String ref) Business Logic คืนสต็อกวัตถุดิบเมื่อมีการยกเลิกอาหารหรือลดจำนวนจาน

destroy() Lifecycle (Composition) วนลูปสั่ง movement.destroy() ทุกตัว ล้าง movements.clear() และตั้ง destroyed = true
จุดสังเกตการออกแบบเชิงวัตถุ (OOP Design Insight):
การที่ Ingredient จัดการตัดสต็อกและบันทึก Movement ภายในตัวเอง ทำให้ Main หรือ Order ไม่จำเป็นต้องรู้สูตรคณิตศาสตร์หรือวิธีสร้าง Movement เลย เป็นไปตามหลัก Information Expert ใน GRASP Pattern
คำถาม-คำตอบยอดฮิตสำหรับการนำเสนอ (Defense Q&A):
ทำไมยอดเริ่มต้นของ Ingredient ถึงเป็น 0? -> เพราะในทางบัญชีสต็อก วัตถุดิบต้องมียอดเริ่มต้นจากการ 'รับเข้า' อย่างเป็นทางการ (ผ่านใบสั่งซื้อหรือยอดยกมา) เพื่อให้มีหลักฐาน Movement บันทึกไว้ตั้งแต่กิโลกรัมแรก

40 }

76 }

81 }

85 quantities.clear();
86 destroyed = true;
87 }

90
91 public int version() { return version; }
92 public String statusText() { return status == RecipeStatus.DRAFT ? "ร่าง" : "สมบูรณ์"; }

บทบาทหน้าที่ (Responsibility): ทำหน้าที่เป็นใบสั่งซื้อวัตถุดิบจากผู้จัดจำหน่าย (PO) ติดตามสถานะตั้งแต่ฉบับร่าง (DRAFT) สั่งซื้อแล้ว (ORDERED) จนถึงตรวจรับสินค้าเข้าคลังจริง (RECEIVED) พร้อมปรับเพิ่มยอดสต็อกอัตโนมัติ

ความสัมพันธ์ UML: PurchaseOrder --(1)--> Supplier, PurchaseOrder --(*)--> Ingredient

ชนิดข้อมูลและการเข้าถึง ชื่อตัวแปร (Field) คำอธิบายหน้าที่ในระบบ
public enum { DRAFT, ORDERED, RECEIVED } PoStatus สถานะใบสั่งซื้อ: DRAFT (ร่าง), ORDERED (ส่งคำสั่งซื้อแล้ว), RECEIVED (ตรวจรับเข้าคลังแล้ว)

private LocalDateTime createdAt วันและเวลาที่ออกใบสั่งซื้อ

ตารางเมธอดสำคัญ (Key Methods & Operations)

รูปแบบเมธอด (Signature) หมวดหมู่การทำงาน คำอธิบายรายละเอียดการทำงาน
PurchaseOrder(String poId, Supplier supplier, Employee by) Constructor สร้างใบสั่งซื้อสถานะ DRAFT พร้อมจดเวลาปัจจุบันและเตรียม List
addItem(Ingredient ing, double qty) Validation / Mutator เพิ่มรายการวัตถุดิบที่ต้องการสั่ง โดยตรวจสอบก่อนว่า supplier.supplies(ing) หรือไม่
markOrdered() State Transition เปลี่ยนสถานะจาก DRAFT เป็น ORDERED เมื่อมีรายการสั่งอย่างน้อย 1 รายการ
receive(List<Double> qtys) Atomic Receiving & Stocking ตรวจรับสินค้าจริง: ตรวจสอบความถูกต้องของตัวเลขทุกรายการให้ครบก่อน แล้วจึงวนลูปเรียก ing.receive(qty, poId, createdBy) เพื่อเพิ่มสต็อกเข้าคลังและเปลี่ยนสถานะเป็น RECEIVED
poId(), supplier(), statusText(), ingredients(), orderedQty(), receivedQty() Accessors อ่านข้อมูลใบสั่งซื้อเพื่อแสดงผล
จุดสังเกตการออกแบบเชิงวัตถุ (OOP Design Insight):
ในเมธอด receive() มีการใช้รูปแบบ Two-Pass Validation (ตรวจผ่านทุกตัวก่อน ค่อยเริ่มอัปเดตสต็อก) ป้องกันปัญหาข้อมูลสต็อกไม่สอดคล้องกัน (Inconsistent State) หากเกิดข้อผิดพลาดกลางคัน
คำถาม-คำตอบยอดฮิตสำหรับการนำเสนอ (Defense Q&A):
ทำไมต้องมีสถานะ ORDERED คั่นกลางระหว่าง DRAFT กับ RECEIVED? -> เพราะในโลกความเป็นจริง เมื่อส่งใบสั่งซื้อไปแล้ว ร้านต้องรอให้ซัพพลายเออร์นำของมาส่ง ซึ่งจำนวนที่ส่งจริงอาจไม่เท่ากับที่สั่ง (Short shipment) จึงต้องมีการกรอก receivedQty ตอนรับจริง

บทที่ 4: การเดินทางของข้อมูลแบบครบวงจร (Life of an Order)

4.1 จำลองสถานการณ์จริง: โต๊ะ T01 สั่งอาหารและคิดเงิน

เพื่อความเข้าใจที่แจ่มชัดที่สุด ให้เราพิจารณากรณีศึกษาตัวอย่าง P4 ตามเอกสาร: ลูกค้าโต๊ะ T01 (ซึ่งเป็นสมาชิก คุณอารมณ์ดี มี 46 แต้ม) สั่งอาหาร 2 รายการ:

  • ผัดกะเพราปลา (M01): 2 จาน @ 69 บาท พร้อมตัวเลือก "เพิ่มไข่ดาว" ทั้ง 2 จาน @ 15 บาท = 2 × (69 + 15) = 168 บาท
  • ยำหมูยอ/แหนม (M02): 1 จาน @ 65 บาท = 65 บาท
  • ยอดรวมทั้งสิ้น: 168 + 65 = 233 บาท

การไหลของข้อมูลในระบบทีละสเต็ป (Step-by-Step Flow):

สเต็ปที่ 1: สแกนโต๊ะและผูกสมาชิก (UC01)
Table t01 ถูกสแกน (qrScanned = true) → สร้าง Customer cus → ค้นพบสมาชิก cus.linkMember(member) → สร้าง Order ord = new Order("ORD-1", t01, cus) ในสถานะ CART

สเต็ปที่ 2: หยิบอาหารใส่ตะกร้า (UC01)
เรียก ord.addItem(kaprao, 2, "เผ็ดกลาง", "ไม่ใส่ชูรส") → สร้าง OrderItem item1 พร้อมคัดลอกสูตรปลา 0.15 กก. ต่อจาน → เรียก item1.addOption(0) เพิ่มไข่ดาว บวกราคาเพิ่ม 15 บาท และเพิ่มไข่ไก่ 1 ฟองในสูตร Snapshot
เรียก ord.addItem(yam, 1, "เผ็ดน้อย", "") → สร้าง OrderItem item2 คัดลอกสูตรหมูยอ 0.5 แท่ง, แหนม 0.5 แท่ง, น้ำยำ 0.1 ลิตร

สเต็ปที่ 3: ตรวจสอบสต็อกและยืนยันออเดอร์ (Two-Pass Confirmation)
เมื่อผู้ใช้กดยืนยัน เรียก ord.confirm():
• Pass 1 (ตรวจสอบ): รวมวัตถุดิบทั้งหมด: ปลาต้องใช้ 0.15 × 2 = 0.30 กก. (มี 5.3 กก. พอ), ไข่ไก่ต้องใช้ 1 × 2 = 2 ฟอง (มี 3 ฟอง พอ), หมูยอ 0.5 แท่ง (พอ), แหนม 0.5 แท่ง (พอ), น้ำยำ 0.1 ลิตร (พอ)
• Pass 2 (ตัดสต็อก): เรียก deduct() ของทุกวัตถุดิบ: ปลาเหลือ 5.0 กก., ไข่ไก่เหลือ 1 ฟอง, หมูยอเหลือ 1.5 แท่ง → แต่ละตัวสร้าง StockMovement ประเภท "ขาย"
• ออเดอร์เปลี่ยนสถานะเป็น CONFIRMED และโต๊ะ T01 เปลี่ยนสถานะเป็น ใช้งาน

สเต็ปที่ 4: ครัวปรุงอาหาร (UC03)
คนครัวรับ item1 เข้าสถานีครัวร้อน เรียก item1.startCooking(cook, 5.0) จดเวลาเริ่ม → ปรุงเสร็จเรียก item1.markReady() จดเวลาจบ
สถานีครัวยำทำ item2 จนพร้อมเสิร์ฟเช่นเดียวกัน

สเต็ปที่ 5: เสิร์ฟอาหาร (UC03)
พนักงานเสิร์ฟ item1.serve(cashier) และ item2.serve(cashier) → เรียก ord.refreshStatus() พบว่าอาหารเสิร์ฟครบทุกจาน ออเดอร์เปลี่ยนสถานะเป็น SERVED

สเต็ปที่ 6: ชำระเงิน คิดแต้ม และปิดบิล (UC04)
แคชเชียร์เลือกออเดอร์ ORD-1 (ยอดรวม 233 บาท) → ลูกค้าใช้ 10 แต้มแลกส่วนลด 10 บาท (ยอดสุทธิเหลือ 223 บาท) → ลูกค้าจ่ายเงินสด 250 บาท (เงินทอน 27 บาท)
เมื่อกดยืนยันชำระเงิน payment.confirm():
• แต้มสมาชิกถูกหัก 10 แต้ม: 46 - 10 = เหลือ 36 แต้ม (สร้าง PointTransaction ประเภท "แลก")
• คำนวณแต้มสะสมใหม่จากยอดสุทธิ: 223 ÷ 50 = 4 แต้ม (ปัดเศษทิ้ง)
• แต้มสะสมเพิ่ม 4 แต้ม: 36 + 4 = ยอดสุทธิสุดท้าย 40 แต้ม (สร้าง PointTransaction ประเภท "สะสม")
• ออเดอร์เปลี่ยนสถานะเป็น PAID และโต๊ะ T01 เปลี่ยนสถานะกลับเป็น ว่าง

สเต็ปที่ 7: รายงานผลการขาย (UC06)
เมื่อผู้จัดการเปิดรายงานยอดขาย ยอดเงินสด 223 บาทจะถูกบันทึกเข้ารายรับของวัน และผัดกะเพราปลาจะถูกนับยอดขาย 2 จาน, ยำหมูยอถูกนับ 1 จานในการจัดอันดับเมนูยอดนิยม

4.2 แผนภาพสถานะ (State Transition Diagram)

เอนทิตี สถานะที่เป็นไปได้ เหตุการณ์ที่ทำให้เปลี่ยน (Trigger) เงื่อนไขสำคัญที่ต้องผ่าน (Guards)
Order CART → CONFIRMED → COOKING → READY → SERVED → PAID สแกนโต๊ะ → confirm() → ครัวเริ่มปรุงจานแรก → ปรุงเสร็จครบ → เสิร์ฟครบ → payment.confirm() ตะกร้าต้องมีอาหาร, สต็อกต้องพอทุกตัว, การชำระเงินต้องทำได้เมื่ออาหารเสิร์ฟครบทุกจานแล้วเท่านั้น
OrderItem WAITING → COOKING → READY → SERVED (หรือ CANCELLED) confirm ออเดอร์ → startCooking() → markReady() → serve() (หรือ cancel() / decideRequest()) ต้องเคยตัดสต็อกจริง, ต้องไม่มีคำขอค้างที่รอผู้จัดการอนุมัติ, หากกำลังปรุงอยู่ต้องผ่านผู้จัดการเท่านั้น
PurchaseOrder DRAFT → ORDERED → RECEIVED สร้างเอกสาร → markOrdered() → receive(qtys) ต้องมีรายการสั่ง, ซัพพลายเออร์ต้องส่งวัตถุดิบนั้นได้, จำนวนรับจริงต้องเป็นตัวเลขครบทุกรายการ
Table ว่าง → ใช้งาน → ว่าง เปิดร้าน → order.confirm() → payment.confirm() โต๊ะต้องผ่านการสแกน QR ก่อนนำรหัสไปเปิดบิล

บทที่ 5: คลังข้อสอบและแนวทางตอบคำถามสำหรับนำเสนอ (Defense Cheatsheet)

รวบรวม 15 คำถามสำคัญที่คณะกรรมการสอบ อาจารย์ผู้ทรงคุณวุฒิ หรือผู้ตรวจประเมินโปรเจกต์มักจะถาม พร้อมแนวทางการตอบที่ถูกต้องตามหลักการวิเคราะห์และออกแบบเชิงวัตถุ (OOAD) และมาตรฐานสถาปัตยกรรมซอฟต์แวร์:

คำถามที่ 1: ทำไมระบบนี้จึงแยก Main ออกจาก 16 คลาสในแพ็กเกจ model?

แนวทางการตอบ: เป็นไปตามหลักการ Separation of Concerns (SoC) และ Single Responsibility Principle (SRP) คลาสใน model มีหน้าที่ดูแลข้อมูล กฎเกณฑ์ทางธุรกิจ และความถูกต้องของตนเอง โดยไม่ขึ้นกับว่าผู้ใช้จะติดต่อผ่านหน้าจอแบบใด ส่วน Main ทำหน้าที่เป็น Presentation และ Orchestrator หากในอนาคตเราต้องการเปลี่ยนหน้าจอจากคอนโซล Text Mode ไปเป็นหน้าเว็บ หรือแอปมือถือ เราสามารถนำคลาสทั้ง 16 ใน model ไปใช้งานต่อได้ทันทีโดยไม่ต้องแก้ไขโค้ดตรรกะธุรกิจเลย

คำถามที่ 2: ทำไมจึงไม่มีการใช้ Inheritance (extends) ระหว่าง 16 คลาสนี้เลย?

แนวทางการตอบ: เพราะคลาสทั้ง 16 ในระบบร้านอาหารนี้มีความสัมพันธ์เชิงธุรกิจแบบ has-a (เป็นเจ้าของหรือรู้จักกัน) ไม่ใช่ความสัมพันธ์แบบ is-a (เป็นชนิดย่อยของกันและกัน) เช่น โต๊ะไม่ได้เป็นลูกค้า, ลูกค้าไม่ได้เป็นออเดอร์, และออเดอร์ไม่ได้เป็นอาหาร การฝืนใช้ Inheritance จะทำให้เกิดสถาปัตยกรรมที่ผิดเพี้ยนและเกิด Coupling สูง เราจึงยึดหลักการสากล "Composition over Inheritance" ตามแนวทางของ Clean OOP

คำถามที่ 3: ทำไมใน Order.confirm() ถึงต้องตรวจสต็อก 2 รอบ (Two-Pass Loop)?

แนวทางการตอบ: เพื่อรักษาความเป็น Atomic Transaction (All-or-Nothing) หากออเดอร์ต้องใช้เนื้อปลาและไข่ไก่ แต่เราวนลูปตรวจเนื้อปลาแล้วตัดเนื้อปลาทันที ก่อนจะไปพบว่าไข่ไก่หมด จะทำให้คำสั่งซื้อล้มเหลวแต่เนื้อปลาถูกตัดไปแล้ว เกิดความเสียหายต่อสต็อกสินค้า ดังนั้นเราจึงต้องใช้ Loop ที่ 1 ตรวจสอบวัตถุดิบทุกชนิดให้มั่นใจว่าพอครบ 100% ก่อน เมื่อผ่านหมดแล้วจึงค่อยเข้า Loop ที่ 2 เพื่อตัดสต็อกจริง

คำถามที่ 4: ทำไม OrderItem ต้องคัดลอกราคาและสูตรมาจาก Menu มาเก็บไว้เอง (Snapshot Pattern)?

แนวทางการตอบ: เพื่อรักษาประวัติศาสตร์และความถูกต้องทางบัญชี หากร้านเปิดมา 1 ปีแล้วผู้จัดการขึ้นราคาผัดกะเพราจาก 69 บาทเป็น 80 บาท หรือเชฟปรับสูตรลดเนื้อปลาลง บิลและประวัติออเดอร์ของลูกค้าเก่าที่เคยสั่งไปเมื่อสัปดาห์ก่อนจะต้องไม่เปลี่ยนราคาและสูตรตามไปด้วย การทำ Snapshot ไว้ใน OrderItem ทำให้ข้อมูลในอดีตคงเดิมอย่างถาวร

คำถามที่ 5: ในภาษา Java มี Garbage Collection อยู่แล้ว ทำไมเรายังต้องเขียนเมธอด destroy() ขึ้นมาเอง?

แนวทางการตอบ: Garbage Collector (GC) ของ Java จะลบอ็อบเจกต์ออกจากหน่วยความจำก็ต่อเมื่อ ไม่มีใครอ้างถึงอ็อบเจกต์นั้นแล้ว แต่ในระดับการออกแบบเชิงตรรกะ (Domain Modeling) เมธอด destroy() ที่เราเขียนขึ้นทำหน้าที่เป็น Lifecycle Cascade Hook เพื่อสะท้อนกฎ Composition อย่างชัดเจน เช่น เมื่อ Order.destroy() ถูกเรียก มันจะสั่ง item.destroy() ทุกตัว และเคลียร์ลิงก์ต่าง ๆ ทิ้ง ทำให้ไม่มีการอ้างอิงค้างอยู่ และช่วยให้ GC สามารถเก็บกวาดหน่วยความจำได้อย่างรวดเร็วและปลอดภัย

คำถามที่ 6: ทำไมฟิลด์กฎแต้มใน Member ถึงประกาศเป็น static แต่ยอดแต้มสะสมเป็นธรรมดา?

แนวทางการตอบ: ยอดแต้มสะสม (points) เป็นของสมาชิกแต่ละคน สมาชิก A มี 40 แต้ม สมาชิก B มี 10 แต้ม จึงต้องเป็น Instance Variable แต่กฎเกณฑ์การคำนวณ เช่น อัตรา 50 บาทได้ 1 แต้ม (bahtPerPoint) หรือ 1 แต้มเท่ากับ 1 บาท (pointValue) เป็นนโยบายการตลาดของร้านที่สมาชิกทุกคนต้องปฏิบัติตามเหมือนกันหมด จึงประกาศเป็น static (Class Variable) ทำให้เมื่อผู้จัดการแก้ไขกฎผ่าน Member.setRule() จะมีผลต่อสมาชิกทุกคนทั้งร้านทันที

คำถามที่ 7: ทำไมใน Recipe ถึงใช้ List 2 ชุด (ingredients และ quantities) แทนที่จะใช้ Map?

แนวทางการตอบ: ตามหลักสูตรการสอนและการอธิบาย OOP ขั้นพื้นฐาน การใช้ List สองชุดที่ตรงกันด้วย Index (Parallel Lists) เช่น ตำแหน่งที่ 0 คือวัตถุดิบปลา และตำแหน่งที่ 0 ของอีก List คือปริมาณปลา 0.15 กก. ช่วยให้ผู้เรียนสามารถไล่ติดตามค่าด้วยลูป for (int i = 0; i < size; i++) ได้อย่างตรงไปตรงมา และไม่ก่อให้เกิดปัญหาเรื่องการเรียงลำดับของ Key เหมือนในโครงสร้าง Map ทั่วไป

คำถามที่ 8: มี Constructor แล้ว ทำไมคลาสต่าง ๆ ยังต้องมีเมธอดอ่านข้อมูล (เช่น name(), stockQty())?

แนวทางการตอบ: เพราะ Constructor ทำงานเพียง ครั้งเดียวตอนสร้างอ็อบเจกต์ (ตอน new) แต่หลังจากสร้างอ็อบเจกต์ขึ้นมาแล้ว โปรแกรมยังต้องมีการทำงานต่อเนื่องอีกยาวนาน เช่น หน้าจอ Main ต้องการนำชื่ออาหาร ราคา ยอดเงิน สถานะ และสต็อกคงเหลือไปแสดงผลให้ผู้ใช้ดู จึงจำเป็นต้องมีเมธอดอ่านข้อมูลเพื่อเปิดช่องทางให้ภายนอกอ่านค่าฟิลด์ที่เป็น private ได้โดยไม่ละเมิด Encapsulation

คำถามที่ 9: ทำไมในคลาสของแพ็กเกจ model ถึงไม่มีคำสั่ง System.out.println() แม้แต่บรรทัดเดียว?

แนวทางการตอบ: เพราะคลาสใน model เป็น Business Entity ที่ไม่ควรผูกติดกับอุปกรณ์แสดงผล (Output Device) หากคลาสโมเดลมีคำสั่งพิมพ์หน้าจอคอนโซล เมื่อนำคลาสนี้ไปใช้งานบนเว็บหรือแอปพลิเคชัน ข้อความเหล่านั้นจะกลายเป็นข้อความขยะในเซิร์ฟเวอร์ หน้าที่การแสดงผลและการจัดรูปแบบข้อความจึงเป็นหน้าที่ของคลาส Main เพียงผู้เดียว

คำถามที่ 10: enum ที่อยู่ในคลาส เช่น OrderStatus หรือ Role ทำให้มีจำนวนคลาสเกิน 16 หรือไม่?

แนวทางการตอบ: ไม่เกินครับ เพราะโครงสร้างไฟล์ในระบบมี 16 ไฟล์ Java ใน src/model พอดี โดย enum ถูกประกาศเป็นสมาชิกภายในคลาสของตนเอง (Nested Enum) เช่น Order.OrderStatus หรือ Employee.Role ทำให้ขอบเขตของ enum ผูกอยู่กับคลาสนั้นอย่างสมเหตุสมผล และไม่มีไฟล์คลาสสนับสนุนแยกย่อยภายนอก

คำถามที่ 11: ทำไมลูกค้าถึงกดยกเลิกอาหารเองไม่ได้เมื่ออาหารเริ่มปรุงแล้ว?

แนวทางการตอบ: เป็นการสะท้อน Business Logic จริงของร้านอาหาร เมื่ออาหารอยู่ในสถานะ WAITING (รอปรุง) พนักงานยังไม่ได้นำวัตถุดิบไปปรุง ลูกค้าจึงยกเลิกได้ทันทีและสต็อกจะถูกคืนเข้าคลัง แต่หากอาหารเปลี่ยนเป็น COOKING (กำลังปรุง) วัตถุดิบได้ถูกใช้ลงกระทะไปแล้ว หากลูกค้ายกเลิกโดยพลการร้านจะขาดทุน จึงต้องออกแบบให้ส่งคำขอพิเศษ (requestChange) ไปยังหน้าจอของผู้จัดการเพื่อให้ผู้จัดการพิจารณาอนุมัติหรือปฏิเสธเป็นกรณีพิเศษ

คำถามที่ 12: การสแกน QR Code โต๊ะใน Terminal ทำงานอย่างไร ทั้งที่ไม่มีกล้องจริง?

แนวทางการตอบ: เป็นการจำลอง (Simulation) โดยในคลาส Table จะมีเมธอด scanTableQRCode() ซึ่งทำหน้าที่ตั้งค่าแฟล็ก qrScanned = true เมื่อผู้ใช้เลือกโต๊ะในหน้าจอ UC01 ระบบจะจำลองว่าลูกค้าได้นำกล้องมาสแกนแล้ว และเมธอด identifyTableNumber() จะยอมคืนรหัสโต๊ะให้เปิดออเดอร์ได้เฉพาะเมื่อแฟล็กนี้เป็นจริงเท่านั้น หากไม่ได้สแกนจะโยน IllegalStateException ออกมาทันที

คำถามที่ 13: ทำไม Customer จึงไม่ถูกลบเมื่อ Order ถูกลบ?

แนวทางการตอบ: เพราะความสัมพันธ์ระหว่าง Order กับ Customer เป็นแบบ Association ลูกค้าเป็นบุคคลภายนอกที่เข้ามาใช้บริการ ในขณะที่ Order เป็นเพียงเอกสารการสั่งอาหาร 1 ครั้ง เมื่อบิลอาหารสิ้นสุดลง ข้อมูลตัวแทนลูกค้ายังคงสามารถคงอยู่ได้เพื่อใช้วิเคราะห์หรือเชื่อมโยงกับบัญชีสมาชิก

คำถามที่ 14: ปัญหา Floating Point ป้องกันอย่างไรตอนตัดสต็อกและคำนวณเงิน?

แนวทางการตอบ: ในการเปรียบเทียบสต็อกของ Ingredient.hasEnough(qty) มีการบวกค่าเผื่อความคลาดเคลื่อน (Epsilon) 0.000001 เข้าไปก่อนเทียบ เพื่อป้องกันข้อผิดพลาดการปัดเศษของเลขฐานสองในชนิดข้อมูล double ส่วนในการคำนวณเงินทอนและยอดสต็อก มีการใช้ฟังก์ชัน Math.round(...) ปัดทศนิยมให้ตรงกับหน่วยสตางค์และหน่วยกรัมอย่างแม่นยำ

คำถามที่ 15: หากระบบไฟดับหรือปิดโปรแกรม ข้อมูลในร้านจะหายหรือไม่ เพราะเหตุใด?

แนวทางการตอบ: ข้อมูลจะหายและกลับไปเริ่มต้นที่ข้อมูลตัวอย่างใหม่ครับ เพราะระบบฉบับนี้เป็นการจำลองสถาปัตยกรรม OOP เชิงตรรกะแบบ In-Memory Collections (เก็บใน RAM ผ่าน ArrayList) เพื่อวัตถุประสงค์ในการศึกษาโครงสร้างอ็อบเจกต์ โดยยังไม่ได้เชื่อมต่อกับระบบจัดเก็บข้อมูลถาวร (Persistent Storage) เช่น ฐานข้อมูล SQL ซึ่งเป็นสเต็ปการต่อยอดในระยะต่อไป

บทที่ 6: บทสรุปและแนวทางการพัฒนาต่อยอดสู่ระดับ Enterprise

6.1 สรุปสาระสำคัญของโครงสร้างระบบ (Project Summary)

ระบบบริหารจัดการร้านอาหาร "ข้าวต้มอารมณ์ดี" ในฉบับ Java OOP 17 คลาสนี้ ได้บรรลุเป้าหมายสำคัญทางวิศวกรรมซอฟต์แวร์และการออกแบบเชิงวัตถุอย่างสมบูรณ์แบบ:

  • ความสอดคล้องกับระเบียบวิธี OOAD: สามารถแปลงโมเดลเชิงแนวคิดจากสไลด์และ Use Cases (P1–P8) สู่อ็อบเจกต์จริงในภาษา Java ได้อย่างถูกต้องครบถ้วนทั้ง 8 งาน
  • การปฏิบัติตามหลักการ Encapsulation: ข้อมูลทั้งหมดถูกปกป้องและเปลี่ยนแปลงผ่านเมธอดที่มีการตรวจสอบกฎเกณฑ์ทางธุรกิจอย่างเข้มงวด
  • ความชัดเจนของ Composition ทั้ง 5 คู่: มีหลักฐานการทำลายวงจรชีวิต (destroy cascade) ที่พิสูจน์ได้จริงในระดับซอร์สโค้ด
  • ความปลอดภัยในการทำธุรกรรม: ใช้รูปแบบ Two-Pass Validation ในการตัดสต็อกและการตรวจรับสินค้า เพื่อป้องกันสภาวะข้อมูลไม่สอดคล้องกัน

6.2 แผนที่การพัฒนาต่อยอดสู่ระบบจริง (Enterprise Modernization Roadmap)

หากต้องการนำระบบนี้ไปพัฒนาต่อยอดเพื่อใช้งานในร้านอาหารจริงในเชิงพาณิชย์ สามารถดำเนินตามขั้นตอนวิศวกรรมซอฟต์แวร์สมัยใหม่ได้ดังนี้:

ระยะที่ 1: การเปลี่ยน In-Memory สู่ Relational Database (JPA / PostgreSQL)

เปลี่ยน ArrayList ใน Main ไปเป็นตารางในฐานข้อมูลเชิงสัมพันธ์ โดยใช้ Spring Data JPA / Hibernate:

  • คลาสโมเดลทั้ง 16 จะถูกใส่คำอธิบายประกอบ (Annotations) เช่น @Entity, @Table, @Id
  • ความสัมพันธ์ Composition จะถูกแปลงเป็น @OneToMany(cascade = CascadeType.ALL, orphanRemoval = true) ซึ่งจะทำหน้าที่เหมือนเมธอด destroy() โดยอัตโนมัติในระดับฐานข้อมูล
  • ความสัมพันธ์ Association จะถูกแปลงเป็น @ManyToOne(fetch = FetchType.LAZY) เพื่อเพิ่มประสิทธิภาพในการสืบค้น

ระยะที่ 2: การพัฒนา RESTful API และ Layered Architecture

ปรับเปลี่ยนสถาปัตยกรรมจากไฟล์ Main เดี่ยว ให้เป็น 3-Tier Layered Architecture:

  • Controller Layer: สร้าง @RestController เช่น OrderController, MenuController เพื่อให้บริการรับส่งข้อมูลในรูปแบบ JSON
  • Service Layer: ย้ายตรรกะการประสานงาน Use Cases จาก uc01() ถึง uc08() ไปอยู่ใน OrderService, PaymentService, StockService พร้อมใส่ @Transactional เพื่อควบคุมความปลอดภัยของธุรกรรม
  • Repository Layer: อินเทอร์เฟซ JpaRepository สำหรับจัดการบันทึกและสืบค้นข้อมูลจากฐานข้อมูล

ระยะที่ 3: ส่วนติดต่อผู้ใช้สมัยใหม่ (Modern UI / UX)

สร้างเว็บแอปพลิเคชันและแอปพลิเคชันบนอุปกรณ์พกพา:

  • Customer Mobile Web (React / Vue): ให้ลูกค้าสแกน QR Code จริงบนโต๊ะผ่านกล้องมือถือ ดูเมนูรูปภาพสวยงาม สั่งอาหาร และติดตามสถานะแบบเรียลไทม์ผ่าน WebSocket
  • Kitchen Display System (KDS): หน้าจอแท็บเล็ตสำหรับคนครัวในแต่ละสถานี แสดงคิวอาหาร จับเวลา และกดแจ้งพร้อมเสิร์ฟ
  • POS Cashier Terminal: หน้าจอสัมผัสสำหรับแคชเชียร์ คิดเงิน สแกนจ่าย Thai QR PromptPay และพิมพ์ใบเสร็จผ่านเครื่องพิมพ์ความร้อน (Thermal Printer)
