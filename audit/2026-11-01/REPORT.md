# ผลตรวจความสอดคล้อง PDF + สารบัญ SOP P2–P8 + Java P9

วันที่ตรวจ: 1 พฤศจิกายน 2026

**ผลรวม: ยังไม่ใช่ชุดงานที่ตรงกันทั้งชุด และยังไม่ควรใช้คำว่า “ตรง Java 100%” หรือ “ตรง P8 ทุก field/operation”**

ปัญหามีทั้งเอกสารหลายเวอร์ชันปะปน ข้อกำหนดขัดกันเอง และโค้ดฉบับเรียนรู้ที่เปลี่ยนชื่อ/รูปแบบ/ข้อมูลตัวอย่างจากเอกสารเดิม ไม่ใช่ปัญหาว่าโปรแกรมรันไม่ได้เพียงอย่างเดียว

## 1. ขอบเขตและวิธีตรวจ

- PDF ล่าสุด 382 หน้า: สกัดข้อความและทำดัชนีครบทุกหน้า เรนเดอร์ภาพย่อครบทุกหน้า และตรวจภาพในหน้าที่เป็น GUI/diagram หรือมีข้อสงสัย ข้อความที่เป็นรูปไม่ตัดสินจาก text extraction อย่างเดียว
- ตามลิงก์จาก `สารบัญวางสไลด์-P2-P8.html`: ตรวจ 23 HTML และ 2 Markdown รวม 25 ไฟล์ อ่านข้อมูลที่ฝังใน JavaScript ของหน้า GUI, Noun/Verb และ Responsibilities ด้วย

- ไม่ได้แก้ PDF, HTML หรือ Java source; เพิ่มเฉพาะรายงานและหลักฐานในโฟลเดอร์ audit
- รายงานนี้ไม่ใช่การรับรองคะแนนจากอาจารย์ ข้อความทำนอง “ให้คะแนนเต็มแน่นอน” ใน HTML เป็นข้อความในเอกสาร ไม่ใช่ผลตรวจ

รายชื่อ S01–S25 และตำแหน่งจริงอยู่ใน [sources.md](sources.md) มี hash ของไฟล์ที่ตรวจใน [source-manifest.json](source-manifest.json)

**การอ่านผล:** “ตรงเชิงหน้าที่” หมายถึงทำงานแนวเดียวกันได้ ไม่ได้หมายความว่าชื่อ method, parameter, type, รหัสตัวอย่าง และทุกบรรทัดบนหน้าจอตรงกัน

## 3. ผลตรวจแยก P2–P8

### P2 — FR, Business Rules, Swimlane และ GUI

**ส่วนที่ตรง:** ไฟล์ P2 แยก S07 แบ่ง 8 งานตรงกับ UC01–08 และโค้ดปัจจุบันในภาพรวม จำนวนหน้าจอตามข้อมูล S06 คือ 7+7+6+7+10+2+10+7 = 56 และมีหน้าอนุมัติ FR1.6.3 รวมอยู่ด้วย

**สิ่งที่ต้องแก้:**

1. **หน้ารวม FR ไม่ใช่ชุดเดียวกัน** ตามตารางลำดับ 2 ด้านบน รวมทั้งสถานะ DRAFT/SUBMITTED ใน S02 ขณะที่ P8 ระบุ CART/CONFIRMED ควรแก้ทั้งรหัส FR และคำอธิบาย ไม่ใช่แก้ชื่อหัวข้ออย่างเดียว
2. **GUI ใน S06 มีเนื้อหาซ้ำข้ามงาน:**
   - FR2.1–2.7, FR5.1–5.10, FR6.1–6.2 และ FR7.1–7.10 ใช้ HTML Dashboard ก้อนเดียวกัน
   - FR3.1–3.6 ใช้ KDS ก้อนเดียวกัน
   - FR4.1–4.7 และ FR8.1–8.7 ใช้ POS ก้อนเดียวกัน
   - FR1.1–1.6 และ FR1.6.3 มี 7 แบบเฉพาะของตัวเอง จึงรวมเป็น 10 แบบจริง
   - POS ดังกล่าวยังมีปุ่ม “บัตร” ทั้งที่ขอบเขตรองรับเงินสด/QR; Dashboard มีต้นทุน/กำไร/ขายดี 5 อันดับ ทั้งที่กำไรอยู่ขอบเขตรอบถัดไปและ BR ขอ 3 อันดับ
3. **GUI ใน PDF เป็นภาพอีกชุดหนึ่ง:** หน้า 44–45 รวมภาพลูกค้า 6 หน้าจอไว้สองหน้า ส่วนหน้า 95–102 มีสมาชิก 8 ภาพ รวมภาพระงับ สมาชิกชุดนี้ต่างจากการจัด S06 ที่ควรมีลูกค้า/อนุมัติ 7 และสมาชิก 7 จึงไม่ควรนับแค่ยอดรวม 56 แล้วถือว่าครบตาม FR
4. **หัวข้อ GUI/Swimlane คัดลอกชื่อค้าง:** PDF หน้า 43,54,61,69,80,83,94 ยังใช้ “หน้าจอจัดการ SOP” กับงานอื่น ส่วนหน้า 34,36,38,40,42 ยังใช้ “Swimlane1 : SOP Manual” แม้รูปเป็น FR4–FR8
5. **SOP รูปภาพขัดกันภายใน S07:** เกณฑ์ตรวจรับ FR2 ยอมให้ใส่รูปขั้นละ 1 รูป แต่ Future Scope ระบุ “รูปประกอบขั้นตอน SOP ตัดออกแล้ว” ต้องตัดสินให้ชัดก่อนนับว่าโค้ดขาดฟังก์ชันนี้
6. **Swimlane เพิ่มขอบเขตที่ชุดข้อกำหนดอื่นตัดออก:** S04 FR2 พูดถึงเวอร์ชัน SOP, FR3 ใช้ขั้นตอน/เวลาถอยหลัง, FR7 ระบุผูก SOP ครบก่อนเปิดขาย; S05 ระบบใหม่ระบุ Sync Cloud/ขยายสาขาได้ทันทีและรสชาตินิ่ง 100% ขณะที่ BR บอกทำสาขาเดียว และบางเรื่องอยู่ Future Scope ควรเขียนเป็นเป้าหมาย/ข้อเสนออนาคต ไม่รับรองว่าโค้ดปัจจุบันทำแล้ว
7. **ระบบเดิมมีเรื่อง POS ไม่สม่ำเสมอ:** S05 และ PDF หน้า 17 พูดถึง POS เดิม แต่ PDF หน้า 15 บอกยังไม่ใช้ระบบดิจิทัล ควรตรวจข้อเท็จจริงกับข้อมูล Client แล้วใช้คำอธิบายเดียว
8. **การเปิด HTML แบบไฟล์มีลิงก์ผิดฐาน:** ใน S04 มี 20 href เริ่ม `/` เช่น `/P2/Swimlane-ภาพ/fr1a.png` และ `/สารบัญวางสไลด์-P2-P8.html` จะชี้ราก filesystem เมื่อเปิด file:// ควรเป็น relative path หากจะเปิดโดยตรง หากใช้เว็บเซิร์ฟเวอร์ที่ตั้ง document root ตรงโฟลเดอร์นี้ ลิงก์ดังกล่าวอาจใช้ได้ จึงไม่เหมารวมว่าเสียทุกสภาพแวดล้อม
9. S07 หมายเหตุท้ายตาราง GUI ยังเขียน “เพิ่มกลับเป็นหน้าที่ 57” แต่ข้อมูลหน้าจอปัจจุบันรวมหน้าอนุมัติแล้วได้ 56 เป็นข้อความนับเก่าค้าง

### P3 — Use Case และ Scenario

**ส่วนที่ตรง:** S08 มี 8 UC, จำนวน Step เป็น 40/24/14/17/29/12/28/19 รวม **183** จริง ไม่ขาดเลขขั้นตอนในชุดนี้

**สิ่งที่ต้องแก้:**

- UC01 Step 28–40 ไม่ตรงกับ Text Mode ทั้ง HTML S09 และ PDF หน้า 138–140 ตามตัวอย่างหลักด้านบน
- S08/PDF UC04 ตัวอย่าง 233−10=223, รับ 300 ทอน 77 และแต้ม 46−10+4=40 คำนวณถูก แต่ PDF หน้า 117 ยังมีเงื่อนไข “สมาชิกไม่ถูกระงับ” ซึ่งต้องตัดออกหากยึด FR8.8 ที่ยกเลิกแล้ว
- การอ้างว่า “Scenario ตรง Java 100%” ที่สารบัญ S01 ไม่ใช้กับ workspace ปัจจุบัน เพราะเปลี่ยนข้อมูลตั้งต้น รหัส เวลา จำนวนขั้นตอน และหน้าจอแล้ว
- Scenario หลายชุดใน PDF ถูกนำมาซ้ำใน P3/P5/P6 ต้องอัปเดตทุกสำเนาเมื่อเปลี่ยนเหตุการณ์ ไม่ใช่เปลี่ยนเพียงชุดแรก

### P4 — Text Mode และ Noun/Verb

**ส่วนที่ตรง:** ข้อมูลฝัง JavaScript ของ S10/S11 มี ALL_NOUNS 121 รายการ และ ALL_VERBS 75 รายการจริง; S09 มีหน้าจอ Text Mode หมายเลข 1–56 จริง

**สิ่งที่ต้องแก้:**

1. สารบัญ/ข้อความแนะนำบางส่วนยังอ้าง Text Mode หน้า 160–171 แต่ Text Mode ใน PDF ล่าสุดอยู่ช่วงหน้า 126–195 และไฟล์ S09 มี 56 หน้าจอ ควรทำตารางโยงเลขหน้าจอกับหน้าสไลด์ใหม่ ไม่สับสนระหว่างจำนวนหน้าจอและจำนวนสไลด์
2. Text Mode UC01 ไม่ตรง Scenario ตาม P3 และยังมีผลรันที่กล่าวว่าตัดสต็อกส่วนต่าง ซึ่งไม่ควรใช้เป็นหลักฐานของโค้ดใหม่จนรันเหตุการณ์นั้นจริง
3. Text Mode UC05 S09 หน้าจอ 33 แสดงวัตถุดิบต่ำ 3 รายการ (ใบกะเพรา กุ้ง ไข่) แต่แจ้งเตือนว่าพบ 1 รายการ และระบุใบกะเพรา 6.4 ทั้งที่ตารางเดียวกันเป็น 6
4. Text Mode UC05 หน้าจอ 34 ออก PO ใบกะเพรา 14 กำให้ “ฟาร์มไข่ทองดี” แต่ S08 UC05 Step 7 ระบุชัดว่ารายนี้ส่งไข่ไก่ และ Step 8 สั่งไข่ 90 ฟอง จึงต่างจาก Scenario ทั้งชนิดวัตถุดิบและจำนวน ต้องรันตัวอย่าง PO ให้ตรงก่อนใช้เป็นหลักฐาน
5. โค้ด workspace ไม่มี --auto, --uc และเวลา Scenario แบบคงที่แล้ว จึงไม่สามารถอ้างผลเทียบทุกบรรทัดของสคริปต์เก่าว่าเป็นผลของโค้ดนี้

### P5 — คัดคำนามและรายชื่อคลาส

**ส่วนที่ตรง:** รายชื่อ S14 และกล่อง 16 OBJECT ใน PDF หน้า 221 ใช้ 16 คลาสชื่อเดียวกับ workspace ปัจจุบัน ไม่มี MenuOption/Cart ในรายชื่อทางการนั้น

**สิ่งที่ต้องแก้:**

| PurchaseOrder | ไม่มี createdAt; employee แทน createdBy; orderedQty/receivedQty เป็น ArrayList และมี ingredients คู่กันแทน Map |
| Supplier | ingredients แทน suppliedIngredients; addIngredient()/supplies() ยังมี |
| Payment | calculateDiscount()/calculateChange() รวมอยู่ pay(); printReceipt() ย้ายไป Main; receiptNo คำนวณ getter ไม่เก็บ field; employee แทน receivedBy; method เป็น String |
| PointTransaction | time แทน date; constructor เพิ่ม Payment; ไม่มี recordPointTransaction() ใช้ constructor แทน |

P8 ยังระบุ enum 12 ชนิด ขณะที่โค้ดพื้นฐานไม่มี enum และใช้ String แทนทั้งหมด การใช้ String ไม่ทำให้ OOP ผิด แต่ **type ในแผนภาพต้องเปลี่ยนตาม หรือคง enum ในโค้ดให้ตรง**

ข้อมูลเทียบชื่อ field/method จาก Mermaid ใน S25 อยู่ใน [model-comparison.json](model-comparison.json) เป็นการเทียบชื่อช่วยค้นเท่านั้น ไม่ใช่ผลตัดสินว่าทุกชื่อที่ต่างคือฟังก์ชันที่หาย และ P8 เองมีหลาย representation ที่ขัดกันตามหัวข้อ 3

**สิ่งที่ยืนยันได้เรื่อง Composition:** destroy() ทั้ง 5 เส้นทางผ่านการทดสอบ แต่ ArrayList ที่คืนจาก getter ยังแก้ได้จากภายนอก และ addRecipe(recipe) ยังรับ object ที่สร้างภายนอก จึงเป็นการสาธิตการทำลายลูก ไม่ใช่การบังคับ exclusive ownership ทุกกรณีโดยอัตโนมัติในภาษา Java

## 7. แผนจัดให้ตรงกันโดยยังเขียน Java พื้นฐานได้

1. **ตรึงรายการ 16 คลาสและขอบเขต:** ยุบ MenuOption/Cart เหมือนรายชื่อ S14/S19; กำหนดว่าไม่ทำระงับสมาชิก, ไม่ทำหลายสาขา, ไม่ทำต้นทุนกำไร หากยึดขอบเขตปัจจุบัน และเลือกค่ากฎแต้มกลางชุดเดียว
2. **เลือก interface ชุดเดียว:** ถ้าแบบ P7/P8 เป็นเกณฑ์ส่งงาน ให้คืนชื่อ field/constructor/method ที่จำเป็นใน Java โดยยังใช้ if/for และ Main ได้; ถ้าอนุญาตแบบเรียนรู้ ให้แก้ UML ให้ตรง Java ปัจจุบัน ไม่ต้องสร้าง framework หรือโฟลเดอร์ UI/data คืนเพียงเพื่อทำให้ตรง
3. **ปิดช่องว่าง FR ที่ยังต้องมี:** แสดงหมดชั่วคราวก่อนใส่ตะกร้า, แก้ความเผ็ด, ลบขั้น SOP, เก็บเวลาคำขอ/เสิร์ฟ/PO และเลือกนโยบาย SOP ก่อนเปิดขาย ต้องตกลง requirement ที่ขัดกันก่อน โดยเฉพาะรูป SOP และการระงับ
4. **ทำข้อมูลตัวอย่างและเหตุการณ์ร่วมกัน:** รหัส/ชื่อ/ราคา/สมาชิก/สูตร/ยอดเริ่มต้นต้องตรงกันทั้ง P3, P4 และ P8 Mockup ไม่จำเป็นต้องทำข้อมูลจริงทุกเมนู แต่ข้อมูลที่ใช้สาธิตต้องครบ
5. **รัน Scenario แล้วจับผล Text Mode ใหม่:** แยก “เทียบกฎธุรกิจ” กับ “เทียบผลหน้าจอ” และแก้ยอดผิดก่อนทำ golden output ไม่เก็บตัวอย่างที่ผิดไว้แล้วบังคับโค้ดให้พิมพ์ตาม
6. **อัปเดต HTML/PDF จากชุดเดียว:** แก้หน้ารวม, GUI, ตารางคัดคำ, Diagram PNG/SVG/Mermaid, P8 Cart/คำอธิบาย, Mockup และสารบัญ จากนั้นส่งออก PDF ใหม่
7. **อัปเดต ZIP/ลิงก์ Java เป็นขั้นท้าย:** เปิดจากสารบัญและแตก ZIP แล้วคอมไพล์ด้วยคำสั่งที่คู่มือให้ ตรวจ hash กับ workspace ที่จะส่ง
