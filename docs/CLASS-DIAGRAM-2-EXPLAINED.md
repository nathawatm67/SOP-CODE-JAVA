## 2. แผนผังการจัดวาง 4 โซน (Quadrants) และความสัมพันธ์ 21 เส้น

เพื่อป้องกันไม่ให้เส้นทับซ้อนกัน แผนภาพจัดแบ่งสถาปัตยกรรมออกเป็น 4 จตุภาค (2x2 Grid) ที่เชื่อมโยงถึงกันอย่างเป็นระบบ:

```
┌──────────────────────────────────────────┬──────────────────────────────────────────┐
│ โซน 1: หน้าร้าน โต๊ะ และออเดอร์ (สีส้ม)     │ โซน 2: ครัว เมนู สูตร และ SOP (สีเขียว/ม่วง)│
│ • Table (โต๊ะอาหาร)                      │ • Menu (เมนูอาหาร) [Whole ②]             │
│ • Customer (ลูกค้า / ผู้สั่ง)              │   ◆──[1..*]──> Recipe (สูตรอาหาร) [Part ②]│
│ • Order (บิลโต๊ะ) [Whole ①]              │ • SOP (คู่มือขั้นตอน) [Whole ③]           │
│   ◆──[1..*]──> OrderItem (รายการ) [Part ①]│   ◆──[1..*]──> SOPStep (ขั้นตอนย่อย) [Part ③]│
├──────────────────────────────────────────┼──────────────────────────────────────────┤
│ โซน 4: แคชเชียร์ แต้ม และพนักงาน (สีฟ้า/น้ำเงิน)│ โซน 3: คลังวัตถุดิบและจัดซื้อ (สีชมพู/ส้ม) │
│ • Payment (การชำระเงินและบิล)            │ • Ingredient (วัตถุดิบ) [Whole ④]         │
│ • Member (สมาชิก/กฎแต้ม) [Whole ⑤]        │   ◆──[0..*]──> StockMovement (ประวัติสต็อก)│
│   ◆──[0..*]──> PointTransaction [Part ⑤] │ • PurchaseOrder (ใบสั่งซื้อ PO)          │
│ • Employee (พนักงาน Hub กลาง)             │ • Supplier (ผู้จัดจำหน่าย) [◇ Aggregation]│
└──────────────────────────────────────────┴──────────────────────────────────────────┘
```

## 3. สรุป Composition 5 คู่แท้ (Solid Diamond ◆)

ทุกคู่เป็น **Strong Aggregate / Pure Composition** ตามนิยาม **OMG UML 2.5.1 Section 11.2.3** และ **Effective Java**:

| ลำดับ | Whole (เจ้าของสิทธิ์) | Part (ส่วนประกอบย่อย) | Multiplicity | บทบาทและการควบคุม Lifecycle ในโค้ด |
|:---:|---|---|:---:|---|
| **①** | **Order** (คำสั่งซื้อ) | **OrderItem** (รายการอาหาร) | `1` ต่อ `1..*` | `Order` สร้าง `OrderItem` ผ่าน `addItem()` เมื่อ `Order.cancel()` หรือ `destroy()` รายการทั้งหมดจะถูกทำลายพร้อมกัน ห้ามแชร์ไปยังบิลอื่น |
| **②** | **Menu** (เมนูอาหาร) | **Recipe** (สูตรอาหาร BOM) | `1` ต่อ `1..*` | `Recipe` เป็นสูตรเฉพาะของเมนูนั้นๆ ผูกพันตามเวอร์ชัน ถ้าเมนูปิดหรือลบ สูตรเวอร์ชันนั้นจะไม่ถูกนำไปใช้เดี่ยวๆ |
| **③** | **SOP** (คู่มือปฏิบัติงาน) | **SOPStep** (ขั้นตอนย่อย) | `1` ต่อ `1..*` | ขั้นตอนการปรุง `SOPStep` มีอยู่เพื่ออธิบาย `SOP` ของเมนูนั้นเท่านั้น ไม่สามารถลอยอยู่นอกคู่มือได้ |
| **④** | **Ingredient** (วัตถุดิบ) | **StockMovement** (ประวัติสต็อก) | `1` ต่อ `0..*` | บันทึก Audit Log ทุกครั้งที่ตัดของ/รับของ/ปรับยอด ถูกสร้างขึ้นจากวัตถุดิบนั้นๆ เป็นประวัติทางบัญชีที่ตัดขาดจากตัววัตถุดิบไม่ได้ |
| **⑤** | **Member** (สมาชิก) | **PointTransaction** (ประวัติแต้ม) | `1` ต่อ `0..*` | สลิปประวัติการได้แต้ม/ใช้แต้ม เป็นสมุดบัญชีส่วนบุคคลของสมาชิกคนนั้น ตายตามบัญชีสมาชิก |

## 5. สคริปต์การนำเสนอและแนวทางการตอบคำถามอาจารย์ (1 ชั่วโมง)

### 🎙️ บทพูดนำเสนอหน้าสไลด์ Class Diagram 2 (พูดประมาณ 1-2 นาที):
> *"อาจารย์ครับ ในส่วนของ Class Diagram 2 (ตามข้อ 1.4 ของโจทย์) เป็นแผนภาพ Detailed Design Class Diagram ที่รวบรวมครบทั้ง 16 คลาสทางการของระบบ โดยแต่ละกล่องคลาสถูกแบ่งออกเป็น 3 Compartments ครบถ้วนตามมาตรฐาน UML 2.5.1:*
> 1. *ชื่อคลาสและคำอธิบายภาษาไทย*
> 2. *Attributes พร้อมระบุ Visibility แบบ Private (`-`) และประเภทข้อมูล (Data Types)*
> 3. *Operations พร้อมระบุ Visibility แบบ Public (`+`), พารามิเตอร์ และ Return Types ที่สอดคล้องกับซอร์สโค้ด Java ในโฟลเดอร์ `src/model/` 100%*
>
> *ความสัมพันธ์ในระบบมีทั้งหมด 21 เส้น โดยกลุ่มความสัมพันธ์หลักที่เราให้ความสำคัญสูงสุดคือ **Pure Composition 5 คู่แท้** ซึ่งแสดงด้วยสัญลักษณ์เพชรทึบสีดำ (◆) ที่ฝั่ง Whole ได้แก่:*
> 1. *Order เป็นเจ้าของ OrderItem*
> 2. *Menu เป็นเจ้าของ Recipe*
> 3. *SOP เป็นเจ้าของ SOPStep*
> 4. *Ingredient เป็นเจ้าของ StockMovement*
> 5. *และ Member เป็นเจ้าของ PointTransaction*
>
> *นอกจากนี้ ยังมี Aggregation (◇) 1 เส้นระหว่าง Supplier กับ Ingredient และ Association แบบ Direct Reference อีก 15 เส้นที่กำกับ Multiplicity ไว้อย่างชัดเจนครับ"*

### ❓ คำถามที่อาจารย์มักจะถามเจาะลึก (Q&A Defense):

- **Q1: "ทำไมใน Class Diagram 2 ถึงไม่มีคลาส MenuOption เหมือนในร่างเดิม?"**
  - **แนวทางตอบ:** *"เพราะเราได้ทำการ Refactor ปรับปรุงความกระชับของสถาปัตยกรรม (Architectural Optimization) โดยยุบ MenuOption เข้าไปเป็น Attribute แบบ `options : Map<String, Double>` ภายในคลาส Menu เพื่อลดความซับซ้อนของคลาสที่มากเกินความจำเป็น และทำให้ใน OrderItem เก็บชื่อออปชันเป็นสตริงเดี่ยวได้โดยตรง ส่งผลให้ระบบคงเหลือ 16 คลาสทางการที่ Clean และทรงประสิทธิภาพที่สุดครับ"*

- **Q2: "สัญลักษณ์เพชรทึบ (◆) กับเพชรโปร่ง (◇) ต่างกันอย่างไรในโค้ด Java?"**
  - **แนวทางตอบ:** *"ต่างกันที่ **Lifecycle Binding** ครับอาจารย์!
    - **Composition (◆ เพชรทึบ):** คลาส Whole จะเป็นผู้ควบคุม Lifecycle ของ Part เช่น `Order` เป็นคน `new OrderItem()` ภายในคลาส และเมื่อ Order ถูกยกเลิกหรือล้าง OrderItem ก็จะถูก Garbage Collected ไปพร้อมกัน ไม่มีการนำไปแชร์ให้บิลอื่น
    - **Aggregation (◇ เพชรโปร่ง):** เช่น `Supplier` กับ `Ingredient` ตัว Supplier ถือรายการ Ingredient เพียงเพื่อบอกว่าร้านนี้สั่งของจากใครได้บ้าง แต่ถ้าเราลบ Supplier คนนั้นทิ้ง วัตถุดิบในคลังก็ยังคงอยู่ ไม่ได้ตายตาม Supplier ครับ"*

- **Q3: "ลูกศร ──▶ บนเส้น Association มีความหมายอย่างไร?"**
  - **แนวทางตอบ:** *"คือ **Navigability (ทิศทางการอ้างอิง)** ครับ ลูกศรชี้ไปทางใดแปลว่าคลาสต้นทางถือ Object Reference ของคลาสปลายทางไว้เป็น Attribute ในตัวมัน เช่น `Order` ──▶ `Table` แปลว่าในคลาส Order มี field `- table : Table` เพื่อเรียกดูว่าออเดอร์นี้เป็นของโต๊ะใดครับ"*
