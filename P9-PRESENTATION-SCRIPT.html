💡 4 กฎทองสำหรับผู้พูด (Golden Rules for Presenter):
1. อย่าอ่านสไลด์ตามตัวหนังสือ: ให้ใช้สายตามองอาจารย์ แล้วชี้หน้าจอตามจุด [ชี้ที่...] ที่ระบุในสคริปต์
2. เน้นคำว่า "ลูกตายตามแม่": ทุกครั้งที่พูดถึง Composition ให้ย้ำว่า "เมื่อตัวแม่ถูกทำลาย ตัวลูกต้องหายไปด้วยทันที"
3. ย้ำว่า Table และ Customer เป็น Association: เพื่อแสดงให้อาจารย์เห็นว่าเราแยกแยะความสัมพันธ์ 2 ชนิดนี้ออกจากกันอย่างแม่นยำ
4. ชูจุดเด่น Clean OOP: ย้ำว่าโปรเจกต์นี้เขียนด้วย Core Java ล้วนๆ ไม่มี Spring Boot หรือ Framework บังสายตา

👁️ ท่าทางและการชี้จอ: 1. ชี้ที่เครื่องหมายข้าวหลามตัดทึบ (◆)
2. ชี้ที่การเปรียบเทียบ Composition vs Association
3. ชี้ที่ Checklist กฎเหล็ก 4 ข้อ

"ก่อนที่เราจะไปดูผลการรันโปรแกรม เราขอเริ่มที่หัวใจสำคัญทางทฤษฎีของระบบ นั่นคือ Composition ครับ"

"หลายคนอาจจะคุ้นชินกับนิยามยาวๆ แต่ถ้าสรุปให้เข้าใจง่ายที่สุดในประโยคเดียว: Composition คือความสัมพันธ์แบบ 'ความเป็นเจ้าของร่วมตาย' ครับ"

"หมายความว่า: เมื่อใดก็ตามที่ไม่มีตัวแม่ ตัวลูกที่เป็นส่วนประกอบย่อยก็อยู่ไม่ได้ ต้องหายไปด้วยกันทันที โดยสัญลักษณ์ข้าวหลามตัดทึบ (◆) จะวางอยู่ฝั่งตัวแม่เสมอ เช่น Order ◆── OrderItem"

"ถ้าเทียบให้เห็นภาพในร้านเราเลยครับ: ถ้าเรากดยกเลิกหรือฉีก ใบออเดอร์ (Order) ทิ้ง รายการอาหารในบิลนั้น (OrderItem) ก็ต้องหายตามไปด้วยทันที นี่คือ Composition แต่ในทางตรงกันข้าม โต๊ะอาหาร (Table) จะไม่หายตาม เพราะโต๊ะเป็นแค่ Association (แค่อ้างถึง)"

"ซึ่งในการเขียนโค้ดภาษา Java เรายึดกฎเหล็ก 4 ข้ออย่างเคร่งครัด ได้แก่: แม่เก็บลูกเป็น private, แม่สั่ง new สร้างลูกเอง, คลาสอื่นห้ามยุ่งกับลูกตรงๆ, และเมื่อแม่ถูกลบ ตัวแม่จะสั่งทำลายลูกทิ้งทั้งหมดครับ"

📝 ข้อความฉบับเข้าใจง่าย (คัดลอกไปอัปเดตสไลด์ 328 ใน Canva ได้เลย):

นิยาม: Composition คือ "ความเป็นเจ้าของร่วมตาย" (ถ้าไม่มีตัวแม่ ตัวลูกต้องหายไปด้วยกันทันที)
สัญลักษณ์: ข้าวหลามตัดทึบ (◆) อยู่ฝั่งตัวแม่เสมอ เช่น Order ◆── OrderItem
กฎโค้ด 4 ข้อ: 1. แม่เก็บลูกเป็น private | 2. แม่ new ลูกเอง | 3. คนอื่นห้ามแตะลูกตรงๆ | 4. แม่ตาย ลูกตายด้วย (items.clear())

หน้า 3 (สไลด์ 329): ตัวอย่างของระบบเรา (src/model/Order.java)

⏱️ เวลาพูด: ~45 วินาที • 🎯 วัตถุประสงค์: ชี้ให้เห็นโค้ดจริงว่าบรรทัดไหนคือ Composition บรรทัดไหนคือ Association
สไลด์ที่ 3 สไลด์ 329 (Canva)
👁️ ท่าทางและการชี้จอ: 1. ชี้บรรทัดที่ 1: private ArrayList<OrderItem> items;
2. ชี้บรรทัดที่ 2: private Table table;
3. ชี้ในเมธอด destroy() ตรง item.destroy() และ table = null;

"สไลด์หน้านี้คือโค้ดจริงในโปรเจกต์ของเราจากคลาส Order.java เพื่อให้เห็นการนำทฤษฎีไปแปลงเป็นโค้ดอย่างชัดเจนครับ:"

"สังเกตที่บรรทัดบนสุด: Order ถือ items ซึ่งเป็น OrderItem เป็น Composition สังเกตว่าในเมธอด addItem() ตัวแม่จะเป็นคน new OrderItem ขึ้นมาเอง และเมื่อเกิดการยกเลิกในเมธอด destroy() ตัว Order จะวนลูปสั่ง item.destroy() และสั่ง items.clear() ทำให้ OrderItem ทั้งหมดถูกทำลายไปพร้อมกัน"

"แต่ในขณะเดียวกัน Order ก็ถือ Table table ซึ่งเป็นเพียง Association (การอ้างถึง) เมื่อออเดอร์ถูกลบ เราแค่เซต table = null เพื่อตัดการเชื่อมโยง แต่ตัว Object โต๊ะอาหารยังคงอยู่ในระบบ ไม่ได้ถูกทำลายตาม และพร้อมรับลูกค้ารายถัดไปได้ทันทีครับ"

เน้นย้ำ: ชี้ให้เห็นความแตกต่างชัดเจนระหว่าง items.clear() (Composition) กับ table = null (Association)

❓ คำถาม 1: ใน Java ไม่มีคำสั่ง delete เหมือนภาษา C++ แล้วเราทำ Composition อย่างไร?
แนวทางการตอบ: "ในภาษา Java การจัดการหน่วยความจำอยู่ภายใต้การดูแลของ Garbage Collector ครับ เราจึงพิสูจน์ความเป็น Composition ผ่าน Life-cycle Method นั่นคือเมธอด destroy() โดยเมื่อ Object ตัวแม่ถูกทำลาย ตัวแม่จะเป็นคนสั่ง clear() และตัดการอ้างอิง Object ลูกทั้งหมด ส่งผลให้ Object ลูกกลายเป็น Unreachable Object และถูก Garbage Collector เก็บกวาดทำลายหน่วยความจำตามไปทันทีครับ"
❓ คำถาม 2: Two-Pass Stock Check ใน FR1 คืออะไร ทำไมต้องทำสองรอบ?
แนวทางการตอบ: "Two-Pass Check คือการแยกกระบวนการตรวจสอบและตัดสต็อกออกเป็น 2 ลูปครับ: รอบที่ 1 (Validation Pass): วนลูปตรวจสอบวัตถุดิบทุกชนิดที่ต้องใช้ในออเดอร์นั้นให้ครบ 100% ก่อนว่าพอหรือไม่ และ รอบที่ 2 (Deduction Pass): เมื่อผ่านรอบแรกครบทั้งหมดแล้ว จึงจะทำการตัดสต็อกจริง เพื่อป้องกันปัญหาตัดสต็อกชิ้นแรกไปแล้ว แต่ของชิ้นถัดไปหมด ทำให้ระบบค้างและสต็อกเสียหายครับ"
❓ คำถาม 3: ทำไม OrderItem ต้องเก็บสำเนาของราคาและสูตรเป็นของตัวเอง ทั้งที่มี Menu อยู่แล้ว?
แนวทางการตอบ: "เพื่อป้องกันปัญหา Historical Data Drift ครับ ในชีวิตจริง ถ้าร้านค้าปรับราคาเมนูผัดกะเพราจาก 69 บาทเป็น 79 บาทในวันพรุ่งนี้ บิลย้อนหลังที่ลูกค้าเคยสั่งไปเมื่อวานจะต้องแสดงราคา 69 บาทเท่าเดิม ไม่ควรเปลี่ยนตาม ดังนั้น OrderItem จึงต้องทำ Snapshot ราคาและสูตร ณ เวลาที่สั่งเก็บไว้ในตัวเองครับ"
❓ คำถาม 4: ทำไมความสัมพันธ์ระหว่าง Order กับ Table หรือ Customer ถึงเป็นแค่ Association ไม่ใช่ Composition?
แนวทางการตอบ: "เพราะเรื่อง Lifecycle และ Ownership ครับ โต๊ะอาหาร (Table) และ ลูกค้า (Customer) มีตัวตนอยู่จริงในร้านค้ามาก่อนที่ออเดอร์จะเกิด และเมื่อออเดอร์นั้นถูกชำระเงินหรือยกเลิกทิ้งไป โต๊ะก็ยังคงตั้งอยู่ที่ร้าน และลูกค้าก็ยังคงเป็นสมาชิกของร้าน ไม่ได้พังหรือหายไปตามออเดอร์ ดังนั้นความสัมพันธ์จึงเป็นแค่ Association (การอ้างถึง) ครับ"
❓ คำถาม 5: ทำไมโปรเจกต์นี้ถึงไม่มีการใช้ Framework เช่น Spring Boot หรือ Lombok?
แนวทางการตอบ: "เพราะเป้าหมายของวิชา OOAD คือการศึกษาและพิสูจน์ความเข้าใจในกลไกพื้นฐานของ Object-Oriented Programming ครับ การใช้ Framework หรือ Annotation สำเร็จรูปจะบดบังกลไกของ Constructor, Encapsulation, Reference, และ Garbage Collection การเขียนด้วย Core Java ล้วนๆ ทำให้เราสามารถอธิบายการทำงานได้ครบทุกบรรทัดอย่างโปร่งใสครับ"
